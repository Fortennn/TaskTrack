# TaskTracker API

Сучасна платформа для управління проєктами, задачами, коментарями та виїзними подіями, побудована згідно з принципами **Clean Architecture** на базі **.NET 10 (C# 12)** та **ASP.NET Core**.

## Практична робота 10 — Інтеграція зовнішнього HTTP API (Geoapify Geocoding)

У межах Практичної роботи 10 реалізовано повноцінну інтеграцію зовнішнього HTTP API для автоматичного геокодування фізичних адрес подій та виїзних завдань у географічні координати (`Latitude`, `Longitude`).

### Контракт інтеграції та самостійне завдання (Self-Study Contract)

1. **Операція провайдера:**
   Перетворення текстової адреси локації (`Location`) у географічні координати через Geoapify Geocoding API (`v1/geocode/search`).
2. **Внутрішній контракт застосунку:**
   Внутрішній малий DTO `Coordinates(double Latitude, double Longitude)` та інтерфейс `IGeocodingService` у шарі `Application`. Шар бізнес-логіки повністю ізольований від `HttpClient`, JSON-структури Geoapify та HTTP-транспорту.
3. **Політика відмови (Graceful Degradation):**
   М'яка деградація: якщо провайдер недоступний, повертає помилку або не знаходить адресу, створення та оновлення задачі/події успішно завершується зі збереженням текстової адреси та значеннями `null` для координат. Бізнес-процес не блокується.
4. **Обмеження очікування (Timeout & Cancellation):**
   - Конфігурований таймаут — 5 секунд.
   - Скасування запиту клієнтом (`CancellationToken.IsCancellationRequested`) негайно перериває виклик без збереження сутності в базі даних (прокидається `OperationCanceledException`).
   - Таймаут клієнта логується як `Warning` та повертає безпечний `null`.
5. **Стратегія кешування (IMemoryCache):**
   - Позитивний кеш: успішно знайдені координати кешуються на **60 хвилин**.
   - Негативний кеш: успішна відповідь провайдера про відсутність збігу (`results: []`) кешується на **10 хвилин**.
   - Нормалізація ключа кешу: видалення зайвих проміжних пробілів та приведення до нижнього регістру (`geo:вул. хрещатик, 1, київ`).
   - Контроль пам'яті: глобальний ліміт `SizeLimit = 1000`, кожен запис має `Size = 1`.
   - Тимчасові збої (429 Too Many Requests, 500, таймаут, мережеві помилки, невалідний JSON) **не кешуються**.
6. **Оновлення сутностей:**
   Під час редагування порівнюються нормалізовані адреси. Якщо адреса не змінилася, наявні координати зберігаються без повторного запиту до зовнішнього API. Якщо адреса змінилася — запитуються нові координати або встановлюється `null` (старі координати не зберігаються).

## Налаштування локального середовища та безпека секретів

Для безпеки API-ключі та конфіденційні параметри не зберігаються у відкритому репозиторії. Використовується механізм `.NET User Secrets`:

```bash
# 1. Ініціалізація сховища секретів (якщо ще не виконано)
dotnet user-secrets init --project src/TaskTracker.Api

# 2. Налаштування локального рядка підключення до PostgreSQL
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=localhost;Port=5432;Database=TaskTrackerDb;Username=postgres;Password=postgres" --project src/TaskTracker.Api

# 3. Налаштування API-ключа Geoapify для геокодування
dotnet user-secrets set "Geocoding:ApiKey" "<ваш-geoapify-api-key>" --project src/TaskTracker.Api
```

У виробничому середовищі (Production / Staging) параметри передаються через змінні середовища:
- `ConnectionStrings__DefaultConnection`
- `Geocoding__ApiKey`

## Тестування без зовнішнього API

Усі тести повністю ізольовані від реальної мережі та зовнішніх провайдерів за допомогою **WireMock.Net** та тестових дублерів (Test Doubles):

```bash
# Запуск повного набору тестів (Unit, Background Tasks, WireMock Geocoding)
dotnet test
```

У тестовий набір входять:
- Позитивні сценарії з валідацією запису в кеш (другий запит не надсилається у мережу).
- Негативний кеш для порожніх відповідей (`results: []`).
- Ізоляція та відсутність кешування для 429 Too Many Requests і 500 Internal Server Error.
- М'яка деградація при пошкодженому JSON та таймауті.
- Перевірка кооперативного скасування через `CancellationToken`.
- Інтеграційні тести оновлення адрес та координат без витоку старих даних.

## Практична робота 11 — Оптимізація запитів та індекси

У межах Практичної роботи 11 реалізовано комплексну оптимізацію запитів, додано складений B-tree індекс, сидер великих наборів даних та усунено надлишкове завантаження даних (over-fetching).

### 1. Засіб початкового заповнення (PerformanceDataSeeder)
- Генерує **100 000 подій** та 10 категорій пакетами по **2 000 записів**.
- Використовує `ChangeTracker.Clear()` після кожного пакета для запобігання витоку пам'яті в `DbContext`.
- Працює **виключно в середовищі Development** (захищено перевіркою `app.Environment.IsDevelopment()`, спроба запуску в іншому середовищі викидає виняток).
- Пригнічує журналювання SQL-команд під час заповнення через конфігурацію в `AddDbContext`.
- Завершує роботу процесу (`return` перед `app.Run()`) без запуску HTTP-сервера.

```bash
# Команда заповнення тестових даних:
dotnet run --project src/TaskTracker.Api -- --PerformanceSeed:Enabled=true --PerformanceSeed:EventCount=100000 --PerformanceSeed:BatchSize=2000 --PerformanceSeed:Reset=true

# Оновлення статистики PostgreSQL:
ANALYZE "Events";
```

### 2. Порівняльний аналіз плану виконання (Before vs After)

Тестовий SQL-запит з обмеженням за діапазоном дат, стабільним сортуванням та пагінацією:
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "Id", "Date", "Title"
FROM "Events"
WHERE "Date" >= '2035-06-15T00:00:00Z'
AND "Date" < '2035-06-16T00:00:00Z'
ORDER BY "Date", "Id"
LIMIT 20;
```

#### Таблиця вимірювань

| Показник | До індексу | Після індексу (`IX_Events_Date_Id`) | Пояснення покращення |
| :--- | :--- | :--- | :--- |
| **Тип сканування** | `Seq Scan on "Events"` | `Index Scan using "IX_Events_Date_Id"` | Повне читання 100k рядків замінено точковим переходом по B-tree |
| **Відкинуто фільтром** | `99 973` | `0` (поле відсутнє) | СУБД читає лише потрібний діапазон листових вузлів (`Index Cond`) |
| **Окремий вузол Sort** | `Sort Key: "Date", "Id"` (quicksort 28kB) | **Відсутній** | Дані в B-tree вже фізично впорядковані за `("Date", "Id")` |
| **Прочитані буфери** | `2134` блоків (~17 MB) | `23` блоки (~184 KB) | Зменшення навантаження на підсистему I/O у **~93 рази** |
| **Execution Time** | `28.88 - 32.25 ms` | `0.27 - 0.95 ms` | Прискорення виконання запиту у **~100 разів** |

### 3. Складений індекс (Composite B-Tree Index)
- Складений індекс `builder.HasIndex(e => new { e.Date, e.Id })` створено через EF Core Fluent API в `EventConfiguration.cs`.
- Згенеровано міграцію `AddEventDateIndex`, метод `Down()` якої містить виключно `DropIndex` (без видалення таблиць/колонок).
- Дотримано правила **leftmost prefix**: перша колонка задовольняє діапазонний фільтр `Date >= ... AND Date < ...`, друга колонка `Id` забезпечує детерміноване впорядкування для стабільної пагінації без необхідності додаткового сортування.

### 4. Усунення Over-fetching через LINQ-проєкцію
- Замість неефективного завантаження повних зв'язаних сутностей через `.Include(e => e.Registrations)` використано чисту проєкцію через `.Select(e => new EventListItem(..., e.Registrations.Count))`.
- EF Core транслює цей вираз у скалярний підзапит `(SELECT count(*)::int FROM "Registrations" WHERE ...)` на стороні бази даних.
- Запити списків використовують `.AsNoTracking()` для мінімізації накладних витрат change tracking.
- Валідація розміру сторінки суворо обмежена `[Range(1, 100)]` в `EventQueryParameters` (запит із `pageSize=101` повертає `400 Bad Request`).

### 5. Самостійне завдання (Оптимізація та індексування сутності TaskItem)
У межах проєкту TaskTracker оптимізовано головний запит списку задач проєкту:
```sql
WHERE "ProjectId" = @projectId AND "CreatedAt" >= @fromUtc
ORDER BY "CreatedAt", "Id"
LIMIT 20;
```
- **Запропонований складений індекс:** `("ProjectId", "CreatedAt", "Id")`.
- **Обґрунтування порядку колонок:**
  1. `ProjectId` — точна рівність (equality prefix), миттєво відсікає задачі інших проєктів.
  2. `CreatedAt` — діапазонний фільтр і порядок сортування (range & sort).
  3. `Id` — детерміноване впорядкування при однакових мітках часу для стабільної пагінації з раннім виходом по `LIMIT 20`.
